1. Class colour legend

Every class on every HTML element falls into one of these categories. Throughout the doc, look at the badge after each class name.

Bootstrap — a class that ships with Bootstrap 5.3. You did not write it; it lives inside node_modules/bootstrap and is included in main.min.css after the SCSS compile. Examples: .row, .col-lg-6, .d-flex, .btn, .card.

Custom — Karim — a class Karim wrote inside the bottom half of sass/main.scss (the section marked "AUTHORED BY KARIM"). Always begins with the buzz- prefix so you know it's project-specific. Examples: .buzz-nav-link, .buzz-icon-btn, .auth-body.

Custom — Malak — a class Malak wrote inside the top half of sass/main.scss (the section marked "AUTHORED BY MALAK") when she introduced Bootstrap. Examples: .text-green, .bg-light-purple, .green-btn, .solid-green-btn.

HTML attribute — not a CSS class, just a standard HTML attribute (type, id, data-*, aria-*, etc.).

The compile pipeline: you edit sass/main.scss → the sass --watch command compiles it to css/main.min.css → every HTML page links css/main.min.css → the browser reads it. You do not edit main.min.css directly because the next save of main.scss overwrites it.

9. js/main.js

Runs on every page. Loads the navbar/sidebar/footer partials, then highlights the active nav link based on URL.

Entry point

document.addEventListener("DOMContentLoaded", async () => {
  await loadPartials();
  highlightActiveNavLink();
  highlightActiveSidebarLink();
});

Three things happen in order:

  1. loadPartials() — fetches the HTML of navbar/sidebar/footer and injects them into their slots.
  2. highlightActiveNavLink() — adds the .active class to the navbar link matching the current page.
  3. highlightActiveSidebarLink() — same idea for sidebar links (Rawan added this for profile pages).
Why await loadPartials() first? Because the navbar HTML doesn't exist in the DOM until after fetch finishes. If we ran highlightActiveNavLink() immediately, it would query for .buzz-nav-link elements that haven't been injected yet and find nothing.

loadPartials()

async function loadPartials() {
  const parts = [
    ["navbar-slot",  "/partials/navbar.html"],
    ["sidebar-slot", "/partials/sidebar.html"],
    ["footer-slot",  "/partials/footer.html"],
  ];
  for (const [slot, url] of parts) {
    const el = document.getElementById(slot);
    if (!el) continue;
    const res = await fetch(url);
    el.innerHTML = await res.text();
  }
}

Walk-through:

  • parts — an array of [slotId, fetchUrl] pairs. Listing them in order means navbar loads before sidebar before footer.
  • for...of — iterate through each pair. slot takes the first element, url the second.
  • document.getElementById(slot) — look up the empty placeholder div on the current page (e.g. <div id="navbar-slot"></div>).
  • if (!el) continue; — skip if a page doesn't have this slot. The auth pages don't have a navbar slot, for example.
  • await fetch(url) — download the partial's HTML text.
  • el.innerHTML = ... — drop the HTML into the empty div, which now becomes the rendered navbar/footer.

highlightActiveNavLink()

function highlightActiveNavLink() {
  let path = window.location.pathname;
  if (path === "/") {
    path = "/index.html";
  }
  document.querySelectorAll(".buzz-nav-link").forEach(link => {
    if (link.getAttribute("href") === path) {
      link.classList.add("active");
    } else {
      link.classList.remove("active");
    }
  });
}
  • window.location.pathname — the URL path without origin (e.g. /pages/contact.html). The root URL / is normalized to /index.html so the home link still highlights when you're at the root.
  • querySelectorAll(".buzz-nav-link") — find all four nav links injected by the navbar partial.
  • If/else — if a link's href matches the current path, add the .active class (CSS draws the green underline). Otherwise remove it. This explicit two-way handling is important when JS adds .active after a re-render.

highlightActiveSidebarLink() (Rawan's addition)

function highlightActiveSidebarLink() {
  const path = window.location.pathname;
  document.querySelectorAll(".buzz-sidebar-link").forEach(link => {
    if (link.getAttribute("href") === path) {
      link.classList.add("active");
    }
  });
}

Same shape as the navbar version, but only adds the .active class — it never removes it. That's fine for full-page navigation (each click reloads the page, classes start fresh) but would need an else-branch if you ever switch to a single-page-app pattern.

10. js/pages/auth.js

Loaded only by the three auth pages. Three independent behaviours: password show/hide, Google/Apple stub buttons, and form submit handlers.

Entry point

document.addEventListener("DOMContentLoaded", () => {
  initPasswordToggle();
  initSocialButtons();
  initAuthForm();
});

initPasswordToggle()

function initPasswordToggle() {
  const toggles = document.querySelectorAll("[data-toggle-password]");

  toggles.forEach(function (btn) {
    btn.addEventListener("click", function () {
      const input = btn.parentElement.querySelector("input");
      if (!input) return;

      if (input.type === "password") {
        input.type = "text";
      } else {
        input.type = "password";
      }
    });
  });
}
  • [data-toggle-password] attribute selector — finds every eye-icon button on the page (currently only on signin).
  • btn.parentElement.querySelector("input") — finds the input inside the same .input-group wrapper as the eye button.
  • Type swap — flipping type between "password" (bullets) and "text" (visible) is a one-line way to toggle visibility without rebuilding the input.

initSocialButtons()

function initSocialButtons() {
  const buttons = document.querySelectorAll("[data-auth-provider]");

  buttons.forEach(function (btn) {
    btn.addEventListener("click", function () {
      const provider = btn.dataset.authProvider;
      console.log("[auth] " + provider + " sign-in clicked — backend not wired yet.");
    });
  });
}

The buttons each carry data-auth-provider="google" or data-auth-provider="apple". btn.dataset.authProvider reads that into a string. Today it just logs to the dev console; once the OAuth backend exists, this line will be replaced with a redirect like window.location.href = "https://accounts.google.com/o/oauth2/...".

initAuthForm()

function initAuthForm() {
  const signinForm = document.getElementById("signinForm");
  const signupForm = document.getElementById("signupForm");
  const forgotForm = document.getElementById("forgotForm");

  if (forgotForm) {
    forgotForm.addEventListener("submit", function (e) {
      e.preventDefault();
      const data = { email: document.getElementById("email").value };
      console.log("[auth] reset-password submitted (dummy):", data);
    });
  }

  if (signinForm) { ... two fields: email + password ... }
  if (signupForm) { ... five fields + matching-password and agreed-to-terms checks ... }
}

Three independent if blocks — only one runs because each page only contains one of the three forms. The shape is the same:

  1. e.preventDefault() — stops the browser from doing its default form-submit (which would reload the page or send to a server).
  2. Read values by ID — explicit list of inputs we care about.
  3. For signup only: guard against mismatched passwords and not-agreed terms before logging the data.
  4. console.log("...") — placeholder for the future fetch("/api/...") call.

11. js/pages/home.js

Tiny script that runs only on index.html. Wires up the Search button click handler for the Flights/Hotels search card. Tab switching itself is handled natively by Bootstrap's pill JS — no code needed for that.

document.addEventListener("DOMContentLoaded", () => {
  initSearchButtons();
});

/* Search buttons (Flights / Hotels tabs).
   For now: each button has data-search-target="..." pointing to the page
   to open on click. Later, this will read the form fields, validate them,
   and either redirect with query params or fetch results from the backend. */
function initSearchButtons() {
  const buttons = document.querySelectorAll("[data-search-target]");

  buttons.forEach(function (btn) {
    btn.addEventListener("click", function () {
      const target = btn.dataset.searchTarget;
      if (target) {
        window.location.href = target;
      }
    });
  });
}
PieceWhat it does
querySelectorAll("[data-search-target]")Finds every button on the page with a data-search-target attribute (the two Search buttons in the Flights and Hotels tab panes).
btn.dataset.searchTargetReads the URL the button should navigate to (e.g. "pages/flight-search.html").
window.location.href = targetTells the browser to load that URL — same as the user clicking a regular link.
Why a <button> with JS instead of just an <a>? Today they're functionally identical. But this structure (real button + JS handler) is the foundation for the eventual real search behavior — once the backend exists, we'll replace window.location.href = target with form-data reading + validation + a fetch call to the search API. The HTML stays the same.
